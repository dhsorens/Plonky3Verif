# Aeneas extraction status (2026-08-06)

Eighth periodic survey (see [`../AENEAS.md`](../AENEAS.md)). **A quiet toolchain
run with one substantive discovery.** The toolchain barely moved on the aeneas
side (**2 commits**, both mechanical: a `charon-pin` bump and a `PrePasses.ml`
change to accept charon's new `Borrowck` statement kind) and moderately on the
charon side (**25 commits**, v0.1.225 → **v0.1.232**). Every catalogued
obstruction reproduces, most of them byte-for-byte: **#9** (charon stack
overflow) still kills `field`/`air`/`commit` on the same
`packed_ext_powers_capped_ty` recursion with the same GAT warning counts;
**#11** (uncaught `CFailure`) still zeroes the Lean output for five crates on
all three known sub-paths at unchanged line numbers; **#7**, **#6**, **#12**,
**#13**, **#14**, **#15** all unchanged. `maybe-rayon` stays clean (0 errors,
exit 0) and `keccak` stays one bug from clean.

The discovery is **#16**, and it is a *reporting* gap rather than a regression:
charon's own post-transformation type checker rejects items in four crates
(`error: Type error after transformations` — `symmetric` 49, `monty-31` 9,
`merkle-tree` 8, `koala-bear` 2), yet charon **exits 0 and writes the `.llbc`
anyway**, so aeneas ingests ill-typed LLBC and reports
`Found type error in the output of charon`. Rebuilding the *previous* charon
(`527ea8e3`) and re-running `symmetric` gives the identical 49 — so this
pre-dates the current delta and was simply missed by earlier surveys, which only
grepped aeneas logs for errors and charon logs for panics. It now has a **7-line
minimal repro** which, as a bonus, is also the first minimal reproducer this
survey has for **#11**.

**Important caveat on the per-crate deltas: the Plonky3 source moved too.** The
repo synced with upstream after the last report (`5303850d`, ~60 upstream
commits, 270 files, +21 428/−7 098), touching **12 of the 13 sample crates**.
Error-count changes are therefore *not* attributable to the toolchain. `air` is
the one crate with **zero** source changes, and its numbers are identical to

toolchain did not move on #9.

## Recommendation

**A holding run on the toolchain, a productive one on evidence.** aeneas
contributed two mechanical commits and charon twenty-five that touched nothing we
track; the only reason this report is not two paragraphs is that the survey
methodology itself had a hole — charon can report type errors and still exit 0 —
and closing it surfaced a real, filable obstruction with the best reproducer this
survey has produced.

1. **File #16 (charon ill-typed LLBC, exit 0).** The highest-value new filing:
   a 7-line dependency-free repro, 68 in-tree occurrences, and it arguably
   contains *two* bugs — the RPITIT associated-type arity mismatch, and charon
   not failing when its own post-transformation type check fails. The second half
   matters beyond us: silent ill-typed output is the worst failure mode for a
   verification front-end.
2. **File #9 (charon stack overflow).** Unchanged and now ten weeks unfiled. This
   run adds the strongest evidence yet that it is not being addressed
   incidentally: `air` has zero source changes and reproduces bit-for-bit across
   25 charon commits.
3. **Add the #16 repro to aeneas [#1164](https://github.com/AeneasVerif/aeneas/issues/1164).**
   That ticket is filed against a `Try` trait bound; our 7-liner drives the same
   crash through sub-path A, and #11 is still the difference between "five crates
   emit nothing" and "five crates emit partial Lean".
4. **File #13 and #14** — carried over, both re-verified on this toolchain, both
   one-liners, and #14 is the only error left in `keccak`.
5. **Comment on aeneas [#176](https://github.com/AeneasVerif/aeneas/issues/176)
   with the #6 group**, cross-referencing #1241. Still the highest-leverage
   aeneas-side fix, and there is now a second reporter describing the same
   pattern.
6. **Revisit the scoping workaround.** charon
   [#1339](https://github.com/AeneasVerif/charon/issues/1339) says
   `--opaque`/`--exclude` cannot reach closure sub-items, which is precisely what
   `--exclude 'p3_field::field::RawDataSerializable'` is meant to suppress. Test
   whether the source-level `#[cfg_attr(charon, charon::opaque)]` route works on
   `into_byte_stream` / `unpack_iter` before relying on the flag.
   [`WORKAROUNDS.md`](WORKAROUNDS.md) has been annotated accordingly.
7. **Closest to clean, unchanged:** `maybe-rayon` (**0 errors, exit 0**, 985
   lines) → `keccak` (2 errors, 1 unique) → `util` (5, but aborts) → `mds` (94) →
   `poseidon2` (180, emits 1742 lines). **Still worth doing next, and now overdue:**
   `lake build` the `maybe-rayon` and `keccak` output to find out whether "0
   errors" means "usable Lean". #15 (missing `Iterator` models) and aeneas #1242
   (items depending on failed translations emitted anyway, producing dangling
   identifiers) both suggest it may not.
8. **Survey hygiene — fixed this run.** Relying on charon's exit code is what hid
   #16 for at least one report cycle. [`run-extract.sh`](run-extract.sh) now
   counts `^error` and `^warning` lines in `charon.log` and prints them in the
   per-crate SUMMARY (`charon errs` / `charon warns`), so a future run cannot
   miss "charon exit 0 with 49 type errors" again. The added lines are purely
   additive — the existing `charon exit` field is unchanged, so the series stays
   comparable. The report table carries this as `OK(N type errors)`.
