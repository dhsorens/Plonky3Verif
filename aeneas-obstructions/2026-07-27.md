# Aeneas extraction status (2026-07-27)

Seventh periodic survey (see [`../AENEAS.md`](../AENEAS.md)). **The largest
substantive delta since 2026-06-04 — and the first crate ever to extract
cleanly.** The toolchain moved a long way (aeneas **+57 commits**, charon pin
**+103 commits** `6f058254` → `527ea8e3`, v0.1.216 → **v0.1.225**), and for the
first time the movement is visible in the artifacts rather than just the commit
log. Three concrete wins: **`maybe-rayon` now extracts with 0 errors and exit 0**
(14 → 0), **`keccak` is down to a single unique error** (3 → 2 occurrences), and
charon's `lift-assoc-types: Inherit supertrait constraints` (`3fa5ef19`,
charon #1326) cut the GAT warning cascade dramatically — `field` 668 → **17**,
`challenger` 121 → **4**. Error counts fell in **every** crate that reaches
aeneas. But the two hard blockers survive: **#9** (charon stack overflow in the
associated-type lift) still kills `field`/`air`/`commit` — now recursing on a
*different* associated type (`packed_ext_powers_capped_ty`, was
`PrimeSubfield`/`Packing`) and, for `air`/`commit`, aborting on the crate itself
rather than transitively on `p3-field`. **#11** (uncaught `CFailure` in
method-signature translation, aeneas #1164) still zeroes the Lean output for five
crates. aeneas's new **preliminary HRTB support** (#1158) is a double-edged
change: it is almost certainly what made `maybe-rayon` clean, and it introduces a
**new** obstruction (**#12**, 34 occurrences in `merkle-tree`) that is already
represented upstream by aeneas #1227. Net: real forward motion on the long tail,
no movement on the two aborts. Still not usable for a campaign.

### Issue #9 — charon stack overflow lifting associated types on `p3-field` (top blocker, still unfiled)
```
warning: Could not compute the value of impl_PackedFieldExtension_ExtField_for_PackedExtField_Binomial
         <@TypeBound(2, 0), @ConstGenericBound(2, 0)>[TraitClauseBound(2, 0)]::packed_ext_powers_capped_ty
         (on impl_PackedFieldExtension_ExtField_for_PackedExtField_Binomial<…>) needed to update item
         reference p3_field::packed::packed_traits::PackedFieldExtension<PackedExtField<…>, …>.
…
thread 'main' (1322718) has overflowed its stack
fatal runtime error: stack overflow, aborting
error: could not compile `p3-field` (lib)   (signal: 6, SIGABRT)
```
charon `527ea8e3` (v0.1.225), `--lift-associated-types='*'`. Unbounded recursion in
`transform/normalize/expand_associated_types.rs` over `p3-field`'s
`PackedFieldExtension` / `PackedExtField` / `BinomialExtensionField` /
`CubicTrinomial` impls. **Changed shape this run:** the cyclic item is now
`packed_ext_powers_capped_ty` (was `PrimeSubfield`/`Packing`), and the warnings show
the instantiation nesting growing monotonically — `@TypeBound(0,0)` →
`@TypeBound(1,0)` → `@TypeBound(2,0)` — which is the recursion made visible.
Charon `3fa5ef19` (#1326, "inherit supertrait constraints") cut the preceding
warning count 668 → 17 on `field` but did not bound the recursion. Blocks
`field`/`air`/`commit`; for `air`/`commit` the abort is on the target crate itself.
A stack overflow gives SIGABRT without unwinding, so **no Rust backtrace is
obtainable** even with `RUST_BACKTRACE=1` (verified this run). **Still the #1
blocker and still has no upstream ticket.**

### Issue #6 — mixed mutually-recursive declaration groups (now the dominant cascade root)
```
[Error] Detected groups of mixed mutually recursive definitions (such as a type
        mutually recursive with a function, or a function mutually recursive with
        a trait implementation):

# Group 1:
- trait decl(field/src/packed/packed_traits.rs:19): p3_field::packed::packed_traits::PackedValue
- type decl(field/src/packed/packed_traits.rs:232): p3_field::packed::packed_traits::PackedValue::unpack_iter::closure

[Error] Mixed declaration groups (which contain both type and function declarations
        or functions and traits, for instance) are not supported yet: [79, 111]
[Error] Mixed-recursive declaration groups are not supported
```
Fires in all 7 `p3-field`-dependent crates that reach aeneas (1 "detected groups" +
1 "mixed declaration groups" each; plus "mixed-recursive" 44 in `challenger`, 8 in
`koala-bear`, 8 in `poseidon2`). The group always pairs the **trait** `PackedValue`
with the **closure type** `PackedValue::unpack_iter::closure` — i.e. a trait is
placed in the same SCC as a closure type generated from one of its own default
method bodies. Everything downstream is stranded, which is why
`Translate.ml:392`/`:299` ("Could not translate the function signature of X because
of previous error") dominates every log. aeneas
[#176](https://github.com/AeneasVerif/aeneas/issues/176) is the closest ticket but
is specifically about *trait × trait* recursion; this is *trait × closure-type*, so
the match is **partial**. **This is now the highest-leverage aeneas-side fix:** it
is the root of the several-hundred-error cascade in seven crates.

long tail is being actively fixed upstream (a crate went to zero errors; every
